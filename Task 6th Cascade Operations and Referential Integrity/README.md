# Практическая работа №6. Каскадные операции и ссылочная целостность

База данных «Biblioteka» из шести таблиц, в которой внешние ключи настроены так, чтобы при
удалении и изменении родительских записей с дочерними происходило ровно то, что требует
задание. Плюс триггер, отвязывающий книги от аннулированного издательства.

Это **отдельная база, а не продолжение `torgash`** из пятой работы. Методичка прямо просит
создать базу «Biblioteka» со своим набором таблиц, пересечений с предыдущей работой у неё
нет.

## Описание решения

```
Solution/
    6_biblioteka.sql    создание базы, шести таблиц, данные и триггер
```

Один файл, а не два: таблицы и триггер здесь неразделимы, триггер опирается на столбец
`status`, который объявлен прямо при создании таблицы издательств.

Данные взяты из методички как есть: 5 авторов, 5 жанров, 3 издательства, 12 книг,
3 читателя и 15 записей о выдаче. Жанры и издательства книгам я расставил сам, в задании
они не расписаны, названия книг и авторы оттуда.

## Как запустить

База поднимается тем же `docker-compose.yml`, что и пятая работа, из корня репозитория.
Обе базы живут в одном контейнере MySQL и не мешают друг другу.

Если контейнер ещё не запускался:

```bash
docker compose up -d
```

Если он уже работает со старым набором скриптов, нужна пересборка. Скрипты выполняются
только при создании тома, на работающей базе новый файл сам не подхватится:

```bash
docker compose down -v
```

```bash
docker compose up -d
```

Дальше http://localhost:8080, сервер `db`, пользователь `root`, пароль `root`. В выпадающем
списке баз появятся обе: `torgash_Холкин` из пятой работы и `Biblioteka` из этой.

Запуск вручную в Adminer или phpMyAdmin: вкладка SQL, а не Импорт. Импорт спотыкается о
`DELIMITER`, без которого не создать триггер.

Проверял на MySQL 8.0.

## Структура базы

| Таблица | Что хранит | Записей |
| --- | --- | --- |
| `avtor` | авторы | 5 |
| `zhanr` | жанры | 5 |
| `izdatelstvo` | издательства и их статус | 3 |
| `chitatel` | читатели | 3 |
| `kniga` | книги, ссылки на автора, жанр и издательство | 12 |
| `vydacha` | выдачи, ссылки на книгу и читателя | 15 |

Порядок создания определён внешними ключами: сначала четыре справочника, затем книги,
последней выдача.

Все таблицы созданы с `ENGINE = InnoDB` явно. Это не формальность: MyISAM разбирает
объявления внешних ключей и молча их игнорирует, и тогда ни одна каскадная операция
работать не будет, а выглядеть всё будет правильно.

Столбцы `kniga.id_zhanr`, `kniga.id_izd` и `vydacha.id_kniga` объявлены допускающими NULL.
Без этого нельзя объявить `ON DELETE SET NULL`: MySQL откажется создавать такой ключ.

## Каскадные правила

| Что происходит | Что должно случиться | Правило |
| --- | --- | --- |
| удалён автор | его книги удаляются | `ON DELETE CASCADE` |
| изменён `id` автора | меняется и у его книг | `ON UPDATE CASCADE` |
| удалено издательство | у книг ничего не меняется | `ON DELETE RESTRICT` |
| удалён жанр | у книг жанр становится NULL | `ON DELETE SET NULL` |
| изменён `id` жанра | у книг ничего не меняется | `ON UPDATE RESTRICT` |
| удалён читатель | его выдачи удаляются | `ON DELETE CASCADE` |
| удалена книга | в выдаче ссылка становится NULL | `ON DELETE SET NULL` |

Два правила стоит пояснить. «У книг ничего не меняется» при удалении издательства означает
`RESTRICT`: сама операция удаления отклоняется, пока на издательство ссылается хоть одна
книга. Других способов ничего не изменить у дочерних записей внешний ключ не даёт, потому
что `SET NULL` и `CASCADE` их как раз меняют.

То же с изменением `id` жанра: `ON UPDATE RESTRICT` не даёт поменять идентификатор, пока на
жанр кто-то ссылается, и книги остаются нетронутыми.

## Триггер

В таблицу издательств добавлен столбец `status` с двумя значениями, по умолчанию
«действующее»:

```sql
status ENUM('действующее', 'аннулированное') NOT NULL DEFAULT 'действующее'
```

Триггер срабатывает после изменения строки и обнуляет внешний ключ у книг этого
издательства:

```sql
CREATE TRIGGER izdatelstvo_after_update
AFTER UPDATE ON izdatelstvo
FOR EACH ROW
BEGIN
    IF OLD.status = 'действующее' AND NEW.status = 'аннулированное' THEN
        UPDATE kniga
        SET id_izd = NULL
        WHERE id_izd = NEW.id_izd;
    END IF;
END
```

`AFTER`, а не `BEFORE`: книги должны отвязаться от уже изменённой строки, а на момент
`BEFORE` новый статус в таблице ещё не записан.

Условие сравнивает старое значение с новым, а не просто проверяет новое. Иначе триггер
срабатывал бы при любом обновлении строки уже аннулированного издательства, включая
переименование, и каждый раз зря бежал бы по таблице книг.

## Проверка

Всё прогнано на MySQL 8 в контейнере. Каждый сценарий выполнялся в транзакции с откатом,
поэтому данные в базе остались исходными.

| Сценарий | Результат |
| --- | --- |
| удалён Толстой | его 2 книги удалены, в таблице осталось 10 |
| `id` Гоголя изменён на 20 | обе его книги получили новый `id` |
| попытка удалить издательство АСТ | отклонена, ошибка 1451, книги не тронуты |
| удалён жанр «Поэма» | у «Мёртвых душ» жанр стал NULL |
| попытка изменить `id` жанра «Роман» | отклонена, ошибка 1451 |
| удалён читатель | его 5 выдач удалены, осталось 10 из 15 |
| удалена книга «Мастер и Маргарита» | все 15 выдач на месте, у двух ссылка на книгу NULL |
| издательство «Эксмо» аннулировано | его 5 книг отвязаны, книги АСТ не тронуты |
| издательство переименовано | книги остались привязанными, триггер не сработал |

Структуру ключей я сверил не глазами, а запросом к `information_schema`: все пять внешних
ключей имеют ровно те `UPDATE_RULE` и `DELETE_RULE`, что в таблице выше.

## Грабли

**Движок.** Пока таблицы создаются без явного `ENGINE = InnoDB`, всё зависит от настроек
сервера. Если по умолчанию окажется MyISAM, внешние ключи будут приняты и проигнорированы,
а проверка покажет, что никакие каскады не работают, хотя код выглядит правильным.

**NULL в столбце внешнего ключа.** `ON DELETE SET NULL` на столбце `NOT NULL` не создаётся
вообще, MySQL отвергает такой ключ при создании таблицы. Это ловится сразу, но сообщение
об ошибке не самое понятное.

**Порядок в скрипте.** Книги ссылаются на три справочника, выдача на книги и читателей, так
что переставить блоки местами нельзя. При запуске по кускам из окна SQL легко выполнить не
в том порядке и получить ошибку создания внешнего ключа.

**Кодировка.** Как и в пятой работе, в начале стоит `SET NAMES utf8mb4;`. Без неё клиент
может прочитать файл в однобайтовой кодировке, и кириллица в данных и в значениях `ENUM`
развалится.
