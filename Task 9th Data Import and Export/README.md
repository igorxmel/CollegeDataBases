# Практическая работа №9. Импорт и экспорт данных пользователя

Две таблицы заполняются из файлов Excel, и две существующие таблицы выгружаются в файлы.
Импорт делает `LOAD DATA INFILE`, экспорт `SELECT ... INTO OUTFILE`. Экспорт здесь тот же,
что в [восьмой работе](../Task%208th%20Data%20Export%20to%20Files): методичка девятой
целиком включает её задание.

## Описание решения

```
Solution/
    9.1_import.sql         две таблицы и два LOAD DATA
    9.2_export.sql         две выгрузки, те же, что в ПР №8
    zakazy.xlsx            результат выгрузки заказов
    zakazchiki_yur.txt     результат выгрузки заказчиков юр.лиц
    Отчёт по ПР №9.docx    отчёт
exchange/                  общая папка обмена с MySQL, в корне репозитория
    postavki.xlsx          исходная таблица для первого импорта
    postavki.csv           она же после «Сохранить как» CSV
    vozvraty.txt           исходный файл для второго импорта
```

Исходные файлы лежат не в `Solution`, а в папке `exchange` в корне репозитория. Это
единственная папка, из которой сервер MySQL разрешает читать файлы, и Docker подключает
её к контейнеру целиком.

## Как запустить

Пересобрать окружение, чтобы сервер увидел папку обмена и скрипты:

```bash
docker compose down -v
```

```bash
docker compose up -d
```

Дальше http://localhost:8080, сервер `db`, пользователь `root`, пароль `root`, база
`torgash_Холкин`. К моменту первого входа обе таблицы уже заполнены: импорт выполняется
при создании базы.

Чтобы показать импорт вживую, достаточно выполнить `9.1_import.sql` во вкладке SQL. Он
пересоздаёт таблицы, поэтому запускается сколько угодно раз.

Экспорт запускается руками, `9.2_export.sql` по одному запросу. Перед повторным запуском
нужно удалить `zakazy.csv` и `zakazchiki_yur.txt` из папки `exchange`, оператор не
перезаписывает существующие файлы. Подробности в [разборе восьмой
работы](../Task%208th%20Data%20Export%20to%20Files/README.md).

## Откуда взялись файлы и данные

Методичка просит создать таблицы самостоятельно, не меньше пяти столбцов с датой, целым,
дробным и текстом, содержимое на русском. Данные придуманы, под магазин «Dream Sneakers»:

| Таблица | Что хранит | Столбцы | Источник |
| --- | --- | --- | --- |
| `postavki` | поставки на склад | ключ, дата, поставщик, категория, количество, закупочная цена | `postavki.xlsx` |
| `vozvraty` | возвраты в магазинах | ключ, дата, магазин, причина, количество, сумма | `vozvraty.txt` |

В каждой по 10 строк. Категории кроссовок те же, что в базе из четвёртой работы по вебу.

Файлы собраны не руками, а скриптом `.claude/tools/build_import_data.py`, причём «Сохранить
как» выполняет настоящий Excel. Поэтому в файлах всё так, как было бы у человека на русском
Windows: кодировка cp1251, даты `ДД.ММ.ГГГГ`, дроби через запятую.

## Разбор импорта

```sql
LOAD DATA INFILE '/var/lib/mysql-files/postavki.csv'
INTO TABLE postavki
CHARACTER SET cp1251
FIELDS TERMINATED BY ';'
ENCLOSED BY '"'
LINES TERMINATED BY '\r\n'
IGNORE 1 LINES
(@data, postavshik, kategoriya, kolichestvo, @cena)
SET data_postavki     = STR_TO_DATE(@data, '%d.%m.%Y'),
    zakupochnaya_cena = REPLACE(@cena, ',', '.');
```

Команда построена по методичке, с одним добавлением: раздел `SET`. Столбцы в скобках
перечислены явно по порядку в файле, и ключа `id_p` среди них нет, его проставляет
`AUTO_INCREMENT`. Первая строка файла это заголовок, её пропускает `IGNORE 1 LINES`.

Дата и цена принимаются не в столбцы, а в переменные `@data` и `@cena`, и разделом `SET`
приводятся к формату MySQL. Зачем это нужно, видно из граблей ниже.

Импорт из `.txt` устроен так же. Отличается разделитель: `.txt` сохранён как текст с
табуляцией, поэтому `FIELDS TERMINATED BY '\t'`, и кавычек нет.

Про `local_infile`. Методичка советует проверить `SHOW VARIABLES LIKE 'local_infile'` и
при значении OFF выполнить `SET GLOBAL local_infile = 1`. Здесь этого не требуется:
переменная относится к `LOAD DATA LOCAL INFILE`, когда файл читается с машины клиента, а
`LOAD DATA INFILE` читает файл на сервере. На этом сервере она выключена, и импорт работает.

## Грабли

Все ошибки ниже получены на настоящем MySQL 8, а не взяты из теории.

**Без `SET` дата не грузится.** Excel записывает `01.09.2026`, а столбец `DATE` ждёт
`2026-09-01`. Результат: ошибка 1292 `Incorrect date value`. На сервере в нестрогом
режиме ошибки нет, и это хуже: вместо неё в таблицу молча попадает `0000-00-00`, то же
самое, что вылезло в пятой работе с `CURDATE()`.

**Без `REPLACE` не грузятся дроби.** Русский Excel пишет `8450,50`. В строгом режиме
ошибка 1366 `Incorrect decimal value`. В нестрогом ошибки нет, а цена молча теряет
копейки: `8450,50` превращается в `8450.00`. Проверено на сервере с пустым `sql_mode`.

**Без `CHARACTER SET cp1251` падает кириллица.** Excel сохраняет в cp1251, и без указания
кодировки сервер читает файл как UTF-8. Ошибка 1300 `Invalid utf8mb4 character string`.

**`\n` вместо `\r\n` ломает не сразу.** Методичка советует `\n` для `.txt`, но Excel
пишет конец строки как `\r\n`, и при `\n` символ `\r` остаётся в конце последнего столбца.
На этих данных загрузка прошла без ошибок, потому что последний столбец числовой, и MySQL
отбрасывает хвостовой `\r` при разборе числа. Будь он текстовым, в значении остался бы
невидимый байт `0D`, и сравнения со строкой перестали бы работать. Проверено на тестовой
таблице. Поэтому в обоих запросах стоит `\r\n`.
