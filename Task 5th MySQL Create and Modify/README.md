# Практическая работа №5. Создание и модификация базы данных в MySQL

Работа из двух частей. В 5.1 создаётся база «torgash» из шести таблиц с ограничениями из
задания, в 5.2 её структура меняется командами `ALTER TABLE` и дополняется триггерами.
Работы под номером 4 в курсе нет, номер пропущен, так что 5.1 и 5.2 это части одной
работы, а не две разные.

По условию имя базы дополняется фамилией, получилось `torgash_Холкин`.

## Описание решения

```
Solution/
    5.1_create.sql         создание базы, шести таблиц и наполнение данными
    5.2_modify.sql         изменение структуры и триггеры
    Отчёт по ПР №5.docx    отчёт, SQL подтягивается в него из этих файлов
```

Отчёт собирается скриптом, который читает `.sql` прямо из этой папки, так что код в
документе не может разойтись с тем, что реально выполняется.

Данные сверены с методичкой построчно: 5 видов собственности, 5 продавцов, 7 физлиц,
7 юрлиц, 21 заказ, 3 скидки, суммы и даты совпадают. Это важнее, чем кажется: преподаватель
смотрит не скрипт, а готовую базу в веб-клиенте, и отдельно просила перенести все данные
из работы.

## Как запустить

Проще всего поднять базу в Docker, он лежит в корне репозитория:

```bash
docker compose up -d
```

Дальше открыть http://localhost:8080, сервер `db`, пользователь `root`, пароль `root`.
Оба скрипта выполняются при первом запуске сами, база `torgash_Холкин` уже наполнена.

После правки любого скрипта нужна пересборка, иначе изменения не подхватятся: скрипты
выполняются только на пустом томе.

```bash
docker compose down -v && docker compose up -d
```

Если запускать руками в Adminer или Workbench, то через вкладку SQL, а не через импорт:
импорт спотыкается о `DELIMITER`, без которого не создать триггеры. Сначала `5.1_create.sql`
целиком, потом `5.2_modify.sql`.

Нужен именно MySQL 8. На MariaDB, которая идёт внутри XAMPP, работа не поднимется:
кириллицу в имени базы она не принимает.

## Что в первой части

Шесть таблиц: виды собственности (`vids`), справочник скидок (`skid`), продавцы
(`salespeople`), заказчики физические лица (`customers_fiz`), заказчики юридические лица
(`customers_yur`) и заказы (`orders`).

Ограничения из задания расставлены там, где они выражаются средствами таблицы: `NOT NULL`,
`UNIQUE`, внешние ключи, `CHECK` на диапазоны (комиссионные от 0,10 до 0,20, рейтинг от
100 до 500, сумма заказа положительная). Всё, что через `CHECK` не выражается, вынесено в
триггеры, про это ниже.

В справочник скидок я добавил столбец `summa` с числовым порогом. В задании условие
записано текстом («Общая стоимость заказов больше 1500 руб»), а триггеру для сравнения
нужно число, и разбирать строку каждый раз дороже, чем хранить порог рядом.

## Что во второй части

Семь изменений структуры через `ALTER TABLE` и триггеры к ним:

| Что требуется | Чем сделано |
| --- | --- |
| уникальность названия продавца | `ADD CONSTRAINT ... UNIQUE` |
| дата регистрации продавца | новый столбец плюс триггер на вставку |
| значение по умолчанию для формы собственности | `ALTER COLUMN SET DEFAULT` |
| возраст заказчика | новый столбец, считается триггером от даты рождения |
| сообщение о пенсионном возрасте | триггер с `SIGNAL` |
| статус юрлица | новый столбец |
| статус по рейтингу | триггеры на вставку и изменение |

Статус выставляется по рейтингу так: от 100 до 200 низкий, от 201 до 400 средний, от 401
до 500 высокий.

## Почему так много триггеров

Это главное, что выяснилось в работе. `CHECK` в MySQL смотрит только на само значение
строки и больше ни на что. Как только условию нужна текущая дата, другая таблица или
старое значение этой же строки, `CHECK` не годится, и остаются триггеры.

Через триггеры сделаны проверка возраста (нужна текущая дата), автоматическая скидка
(нужен справочник), запрет менять уже внесённые комиссионные, пол и дату рождения (нужно
старое значение строки) и бесплатная доставка для заказов дороже 11000 рублей (нужно
посчитанное поле). MySQL к тому же прямо запрещает `CURDATE()` внутри `CHECK` и внутри
вычисляемых столбцов.

Код, которым прерывается операция, решает, попадёт запись в базу или нет:

```sql
SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Регистрация только с 18 лет';
```

`45000` прерывает операцию, строка не вставляется. Код `01000` это предупреждение: текст
виден в `SHOW WARNINGS`, но строка всё равно попадает в базу.

## Грабли

**Пенсионеры проходили в базу.** Сначала сообщение про пенсионный возраст я сделал через
`01000`, прочитав формулировку «предусмотреть вывод сообщения» как предупреждение. На
защите выяснилось, что запись не должна попадать в базу вовсе, и код пришлось менять на
`45000` прямо на паре. Вывод на будущее: если по смыслу запись не должна оказаться в базе,
то `45000`, а не предупреждение.

**`CURDATE()` в значении по умолчанию не отработал.** Столбец `data_reg`, объявленный через
`DEFAULT (CURRENT_DATE)`, при вставке получал `0000-00-00`. Теперь дата проставляется
триггером `BEFORE INSERT`, и это работает.

**Кириллица разваливалась при запуске скрипта из файла.** `CREATE DATABASE torgash_Холкин`
падал с ошибкой синтаксиса: файл честный UTF-8, но клиент читал его в однобайтовой
кодировке. Лечится первой строкой скрипта:

```sql
SET NAMES utf8mb4;
```

Она теперь стоит в обоих файлах и пригодится при любом запуске из клиента.

**Сама база создаётся с `utf8mb4` и сортировкой `utf8mb4_general_ci`.** С ними русские
данные и русское имя базы работают нормально.
