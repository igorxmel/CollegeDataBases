# Практическая работа №7. Работа с объектами базы данных

Работа из четырёх частей, все на базе `torgash_Холкин` из пятой работы. Сорок два запроса
на выборку: от условий и агрегатных функций до группировки, соединения нескольких таблиц,
подзапросов, объединения и операторов ANY и ALL. Результат каждого запроса по условию
сохраняется в представление.

Файл на часть, как методички. Представления названы по номеру части и пункта: `v7_1_01`,

Отчёт содержит ровно то, что просит методичка: текст задания и реализующий его запрос.
Запросы в него подтягиваются из этих файлов при сборке, поэтому разойтись не могут.

## Как запустить

База поднимается тем же `docker-compose.yml` из корня репозитория, скрипты всех четырёх
частей подключены и выполняются при создании базы:

```bash
docker compose down -v
```

```bash
docker compose up -d
```

Дальше http://localhost:8080, сервер `db`, пользователь `root`, пароль `root`, база
`torgash_Холкин`. Представления видны в списке рядом с таблицами, открываются щелчком.

Вручную в Adminer или phpMyAdmin: вкладка SQL, по файлу за раз, в порядке номеров.
База из пятой работы должна существовать до запуска.

## Решения, которые стоит пояснить

**Первая половина алфавита** (7.1, пункт 6) взята как буквы от А до Н включительно. В
задании граница не названа, а в русском алфавите 33 буквы, поэтому деление пополам
неточное в любом случае.

**Городской телефон** (7.3, пункт 6) отличается от мобильного кодом в скобках: в данных
пятой работы городские записаны как `+7 (831) 224-16-16`, мобильные как
`8-900-375-15-65`. Отбор идёт по наличию скобки.

**Время года** считается по месяцу через `CASE`: зима это 12, 1, 2, дальше по три месяца.
Отдельного столбца с сезоном в базе нет.

**Самый молодой мужчина и женщина** (7.2, пункт 2) выбираются сравнением пары «пол и дата
рождения» с результатом группировки. Простая группировка по полу с выводом имени здесь
даёт неверный результат: имя берётся из произвольной строки группы, а не из той, где
максимальная дата рождения. Методичка в конце предлагает отключить `sql_mode`, чтобы такой
запрос вообще выполнился, но неправильным он от этого быть не перестаёт.

## Проверка

Все четыре файла выполнены на MySQL 8 в контейнере, 42 представления создались без
ошибок, пустых среди них нет. База пересобрана с нуля одной командой, в журнале запуска
ошибок нет.

Выборочно сверил результаты с данными вручную: самый дорогой продавец это Семёнов с суммой
34167.05, город с максимальным суммарным рейтингом это Самара с 500, меньше всего заказов
летом (2), комиссионные выше казанских у Монтажа и Костина.

**Одно место даёт вырожденный результат не по вине запроса.** Пункт 3 части 7.3 просит
заказы самой молодой компании-продавца. В пятой работе дата регистрации проставляется
триггером как текущая дата, и скрипт модификации заполнил её всем продавцам одинаково.
Поэтому «самая молодая» компания не определяется, и запрос возвращает все заказы.
Сам запрос написан правильно, упирается он в данные. Если понадобится осмысленный вывод,
достаточно проставить продавцам разные даты регистрации в пятой работе, но та работа уже
сдана, и я её не трогал.
