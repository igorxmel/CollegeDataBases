# Вариант 1 — подсистема «Склад и материалы» компании «Мозаика»

Решение задания демонстрационного экзамена по специальности 09.02.07
(шифр варианта `В1_КОД 09.02.07-2-2025-ПУ`). Производственная компания «Мозаика»
выпускает керамическую плитку; разрабатывается подсистема учёта материалов
(сырья) с просмотром списка материалов, добавлением и редактированием данных
о материале и просмотром списка поставщиков материала.

## Стек

| Что | Чем |
| --- | --- |
| СУБД | SQLite 3 — файл базы `database/mosaic.db`, не требует сервера |
| Язык | Python 3.12, именование `snake_case` согласно требованию к оформлению кода |
| Интерфейс | tkinter (входит в стандартную поставку Python) |
| Подготовка данных | openpyxl — чтение файлов заказчика `*_import.xlsx` |
| ER-диаграмма | reportlab — вывод схемы из служебных таблиц SQLite в PDF |

Внешние зависимости нужны только для пересборки базы и диаграммы. Само
приложение работает на стандартной библиотеке.

## Запуск

```bash
pip install openpyxl reportlab
```

Пересобрать базу данных из файлов заказчика и ER-диаграмму (готовые файлы уже
лежат в репозитории, шаг нужен только при изменении исходных данных):

```bash
cd database && python build_database.py && python make_er_diagram.py
```

Запустить приложение:

```bash
cd app && python main.py
```

В Windows то же самое делает `run.bat`. Готовый исполняемый файл лежит в
`dist/`, пересобрать его можно через `python build_exe.py` (нужен `pyinstaller`).
Файл `mosaic.db` должен находиться рядом с `.exe`.

Тесты расчётов:

```bash
python -m unittest discover -s tests -v
```

## Модуль № 1. База данных

### Схема

Создано 18 таблиц, охватывающих все подсистемы описания предметной области
(Приложение 1): продукция, склад и материалы, производство, сотрудники,
партнёры. Подсистема «Склад и материалы», по которой написано задание модуля
№ 1, заполнена данными заказчика; остальные подсистемы описаны структурно.

| Таблица | Назначение | Пункт |
| --- | --- | --- |
| `unit` | справочник единиц измерения: кг, л | п.7 |
| `material_type` | типы материалов и процент потери сырья при производстве | п.7 |
| `product_type` | типы продукции и коэффициент типа продукции | п.10 |
| `organization_type` | организационно-правовые формы (ООО, ЗАО, ОАО, ПАО) — общий справочник для поставщиков и партнёров | п.1, п.9 |
| `job_position` | должности сотрудников: менеджер, мастер производства, аналитик, кладовщик | п.2, п.5 |
| `request_status` | статусы заявки: создана, ожидает предоплаты, в производстве, готова к отгрузке, выполнена, отменена | п.3 |
| `supplier` | поставщики материалов: наименование, форма собственности, ИНН, рейтинг, дата начала работы | п.9 |
| `material` | материалы (сырьё): тип, единица измерения, цена, остаток, минимум, упаковка, описание, изображение | п.7 |
| `material_supplier` | какой поставщик поставляет какой материал — связь «многие ко многим» | п.7, п.9 |
| `stock_movement` | движение материала на складе: поступления от поставщика и списания в производство | п.7–9 |
| `employee` | сотрудники: ФИО, дата рождения, паспорт, банковские реквизиты, наличие семьи, состояние здоровья, должность | п.4 |
| `product` | продукция: артикул, тип, описание, изображение, минимальная цена для партнёра, размеры и вес упаковки, сертификат, номер стандарта, время изготовления, себестоимость, цех, число рабочих | п.10 |
| `product_material` | необходимые материалы для производства продукции с нормой расхода на единицу | п.10 |
| `production_batch` | партия продукции, запущенная в производство: мастер, количество, даты начала и окончания | п.5, п.8 |
| `partner` | партнёры: форма собственности, наименование, юридический адрес, ИНН, директор, телефон, email, логотип, рейтинг | п.1 |
| `partner_sale` | история реализации продукции партнёром — основа для расчёта скидок | п.1–2 |
| `request` | заявка партнёра: менеджер, статус, способ получения, даты предоплаты, оплаты и выполнения | п.3 |
| `request_item` | позиции заявки: продукция, количество, стоимость и дата производства каждой единицы | п.3 |

Задание разрешает не воспроизводить все сущности предметной области, поэтому
детализация, не влияющая на подсистему материалов, намеренно опущена: система
турникетов и карт доступа (п.6), допуск к конкретному оборудованию (п.5),
отдельные таблицы мест продаж и истории изменений рейтинга партнёра (п.1–2),
история изменений минимальной стоимости продукции (п.10). Там, где справочник
избыточен, использовано ограничение `CHECK`: способ получения продукции
(`request.delivery_type`) принимает только «Доставка» или «Самовывоз».

Подсистема материалов покрывает п.7 полностью: `material.description` и
`material.image_path` — описание и изображение материала, а `stock_movement` —
«история изменений количества материалов на складе» (п.7) и «история поставок
материалов» (п.9) одновременно: поставка от конкретного поставщика это движение
с заполненным `supplier_id`.

### Нормализация

- **1НФ** — все атрибуты атомарны, повторяющихся групп нет. Список поставщиков
  материала, который в исходном файле идёт перечислением, вынесен в отдельную
  таблицу `material_supplier`; размер упаковки продукции хранится тремя полями
  `package_length`, `package_width`, `package_height`, а ФИО сотрудника — тремя
  полями вместо одной строки.
- **2НФ** — у составных ключей (`material_supplier`, `product_material`)
  неключевые атрибуты либо отсутствуют, либо зависят от ключа целиком:
  `quantity_per_unit` — это норма расхода именно пары «продукция + материал».
- **3НФ** — устранены транзитивные зависимости: процент потери сырья зависит от
  типа материала, а не от материала, поэтому он хранится в `material_type`;
  коэффициент типа продукции — в `product_type`; так же вынесены единица
  измерения (`unit`), форма собственности (`organization_type`), должность
  (`job_position`) и статус заявки (`request_status`). Изменяемые во времени
  величины вынесены в таблицы истории (`stock_movement`, `partner_sale`),
  а не дублируются в основных таблицах.

Ссылочная целостность обеспечена 21 внешним ключом: `ON DELETE RESTRICT` для
справочников и для данных, которые нельзя терять вместе с родителем,
`ON DELETE CASCADE` для подчинённых записей (позиции заявки, продажи партнёра,
таблицы связей) и `ON DELETE SET NULL` для необязательных ссылок — например,
`stock_movement.supplier_id`: движение остаётся в истории, даже если запись о
поставщике удалена. В SQLite проверка внешних ключей включается директивой
`PRAGMA foreign_keys = ON` — она есть и в скрипте схемы, и в коде приложения.
Дополнительно расставлены ограничения `CHECK` (неотрицательные цены и
количества, положительный размер упаковки, ИНН из 10 или 12 цифр, дата без
времени, способ получения продукции из двух допустимых значений) и `UNIQUE`
на наименования, артикулы и ИНН.

### Импорт данных

`build_database.py` читает пять файлов заказчика и готовит их к загрузке:

- обрезает пробелы в наименованиях (в `Suppliers_import.xlsx` часть названий
  записана с завершающим пробелом — иначе связи с материалами не сойдутся);
- округляет цену единицы материала до двух знаков (в исходных данных встречаются
  значения вида `17.666666666666668` и `303.63839999999999`);
- переводит дату начала работы с поставщиком из формата Excel в ISO-8601;
- собирает справочники `unit` и `supplier_type` из значений, встречающихся в
  данных, и подставляет вместо текстовых значений внешние ключи;
- проверяет, что связи не ссылаются на несуществующие материалы и поставщиков,
  и прекращает загрузку с понятным сообщением, если это не так.

Загружено: 20 материалов, 20 поставщиков, 80 связей «материал — поставщик»,
5 типов материалов, 4 типа продукции, 2 единицы измерения, 4 формы
собственности.

Дополнительно заполнены два справочника, значения которых прямо названы в
описании предметной области: должности (п.2, п.5, п.8, п.9) и статусы заявки
(п.3). Остальные таблицы остальных подсистем созданы пустыми: заказчик передал
файлы импорта только по материалам, поставщикам и типам, поэтому данные за него
не выдумываются.

Файл базы данных может быть открыт в клиенте СУБД и потому заблокирован для
удаления — в этом случае скрипт не падает, а очищает содержимое базы на месте
и создаёт схему заново.

### ER-диаграмма

`er_diagram.pdf` содержит все 18 таблиц, их атрибуты, отметки первичных (PK) и
внешних (FK) ключей и 21 связь с указанием кардинальности; блоки сгруппированы
по подсистемам предметной области. Диаграмма строится скриптом из
`PRAGMA table_info` и `PRAGMA foreign_key_list` реальной базы, поэтому
расходиться со схемой она не может: вручную задано только распределение таблиц
по колонкам, а координаты блоков, линии связей и размер листа рассчитываются
автоматически. Если таблицу добавить в схему и забыть разместить на диаграмме,
скрипт остановится с сообщением об этом.

## Модуль № 2. Список материалов и стоимость партии

Главная форма выводит материалы карточками по макету из задания:

```
Тип | Наименование материала
Минимальное количество: 1000 кг
Количество на складе:   1000 кг
Цена: 1000,00 р / Единица измерения: кг      Стоимость партии: 0,00 р
```

### Расчёт стоимости минимально необходимой партии

1. Если остаток на складе не меньше минимально допустимого количества, закупка
   не нужна и стоимость партии равна `0,00 р`.
2. Иначе считается недостающее количество: `минимум − остаток`.
3. Недостача округляется **вверх** до целого числа упаковок, потому что материал
   закупается упаковками: `объём = ⌈недостача / размер упаковки⌉ × размер упаковки`.
4. Стоимость партии `= объём × цена единицы материала`, округление до копеек.

Пример (Гидрослюда): минимум 3500 кг, на складе 2147 кг, упаковка 25 кг,
цена 17,20 р. Недостача 1353 кг → 55 упаковок → 1375 кг → **23 650,00 р**.

Все расчёты идут в `Decimal`, а не в числах с плавающей точкой: иначе деление
недостачи на размер упаковки даёт погрешность и округление вверх срабатывает на
одну упаковку больше. Стоимость всегда неотрицательна и содержит два знака после
запятой.

### Оформление

Приложение следует руководству по стилю из Приложения 2: шрифт Comic Sans MS,
основной фон `#FFFFFF`, дополнительный `#ABCFCE`, акцент целевых действий
`#546F94`. На главной форме стоит логотип компании (уменьшен целым делителем,
поэтому пропорции и цвет не искажены), у окна установлена иконка `Мозаика.ico`.

## Модуль № 3. Интерфейс и обработка ошибок

Навигация последовательная: формы открываются стопкой, кнопка «← Назад» в шапке
возвращает на предыдущую форму и обновляет её данные. Заголовок окна и заголовок
на форме меняются вместе со страницей — «список материалов», «добавление
материала», «редактирование материала», «поставщики материала».

Переходы на форму материала: нажатие на карточку открывает редактирование,
кнопка «Добавить материал» — добавление. При открытии на редактирование все поля
заполняются значениями выбранного материала из базы данных. После сохранения
список материалов обновляется.

Поля формы: наименование, тип материала (выпадающий список), количество на
складе, единица измерения, количество в упаковке, минимальное количество, цена
единицы материала. Под каждым полем — подсказка о допустимых значениях.

Проверки и сообщения:

| Ситуация | Тип окна | Что сообщается |
| --- | --- | --- |
| Пустое наименование, тип или единица измерения | Предупреждение | какое поле не заполнено и что в него ввести |
| Нечисловое значение в числовом поле | Предупреждение | какое значение отвергнуто и пример правильного |
| Отрицательная цена или минимальное количество | Предупреждение | что отрицательные значения недопустимы |
| Больше двух знаков в цене | Предупреждение | до скольких знаков округлить |
| Количество в упаковке ≤ 0 | Предупреждение | значение должно быть больше нуля |
| Материал с таким наименованием уже есть | Ошибка | предложение изменить наименование |
| Успешное сохранение | Информация | что именно сохранено |
| Выход с формы с несохранёнными изменениями | Предупреждение с вопросом | подтверждение потери изменений |
| Закрытие приложения | Предупреждение с вопросом | подтверждение выхода |
| Непредвиденная ошибка в обработчике события | Ошибка | описание и порядок действий, приложение продолжает работать |

Аварийного завершения не происходит: неперехваченные исключения обработчиков
событий перехватываются `report_callback_exception`, отсутствие файла базы или
занятость его другим процессом обрабатываются при запуске.

## Модуль № 4. Поставщики материала и расчёт количества продукции

### Список поставщиков

С карточки материала кнопка «Поставщики материала» открывает форму со списком
поставщиков этого материала: наименование, рейтинг, дата начала работы. Список
отсортирован по убыванию рейтинга. Форма оформлена в том же стиле, имеет
заголовок и возврат к списку материалов. Если поставщиков нет, выводится
поясняющий текст вместо пустой таблицы.

### Метод расчёта количества продукции

`app/product_calculation.py` — отдельный модуль, чтобы его исходный код можно
было выгрузить в отдельный репозиторий системы контроля версий.

```python
calculate_product_quantity(
    product_type_id,    # идентификатор типа продукции, целое число
    material_type_id,   # идентификатор типа материала, целое число
    material_quantity,  # количество используемого сырья, целое число
    first_parameter,    # первый параметр продукции, вещественное число > 0
    second_parameter,   # второй параметр продукции, вещественное число > 0
    repository,         # источник справочников типов продукции и материалов
) -> int
```

Расчёт:

1. `сырьё на единицу = параметр 1 × параметр 2 × коэффициент типа продукции`;
2. `сырьё с потерями = сырьё на единицу × (1 + процент потери сырья)`, процент
   берётся из типа материала;
3. результат — целая часть от `количество сырья / сырьё с потерями`.

Пример: тип продукции с коэффициентом 1,2, тип материала с потерями 0,0012,
параметры 2,0 и 3,0, сырья 1000. Сырьё на единицу — 7,2; с потерями — 7,20864;
`1000 / 7,20864 = 138,72…` → **138 единиц продукции**.

Метод возвращает `-1`, если тип продукции или тип материала не найден, если
идентификаторы или количество сырья не целые числа (либо отрицательные), если
параметры продукции не положительные вещественные числа. Количество сырья,
равное нулю, допустимо и даёт 0 единиц продукции.

### Тесты

`tests/test_calculations.py` — 20 тестов: округление закупки до целых упаковок,
неотрицательность и два знака в стоимости партии, форматирование сумм и
количеств, расчёт количества продукции с потерями и все случаи возврата `-1`,
а также проверка расчётов на реальных данных заказчика из `mosaic.db`.

выделен в отдельный файл `app/product_calculation.py`.
